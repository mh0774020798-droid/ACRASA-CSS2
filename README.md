# 🚀 בדיקת מהירות האתר עוגן פליי

בדיקת עומס מדורגת של [עוגן פליי](https://ogenplay.com/) עם לוגים ודוחות בעברית. התרחיש מבקש רק את עמוד הבית, אינו מתחבר לחשבונות ואינו משנה מידע באתר.

## ⏰ בדיקה אוטומטית כל כמה שעות — גם כשהמחשב כבוי

נוסף workflow ייעודי: [⏰ בדיקת עומס אוטומטית — עוגן פליי](.github/workflows/scheduled-load-test.yml). ברירת המחדל היא בדיקה כל **4 שעות**, בדקה 17 של השעה, לפי שעון ישראל (`Asia/Jerusalem`). הוא רץ על GitHub Actions; אין צורך להשאיר מחשב פתוח.

**התזמון כבוי כברירת מחדל.** כדי להפעיל אותו פעם אחת ולהשאירו פועל, פתחו את [Settings → Secrets and variables → Actions → Variables](https://github.com/mh0774020798-droid/ACRASA-CSS2/settings/variables/actions), לחצו **New repository variable**, והוסיפו את המשתנים הבאים:

| שם המשתנה | ערך התחלתי | מה הוא עושה |
| --- | --- | --- |
| `OGENPLAY_SCHEDULE_ENABLED` | `true` | מפעיל את התזמון |
| `OGENPLAY_SCHEDULE_AUTHORIZED` | `true` | מאשר מראש בדיקות באתר שבבעלותכם או שיש לכם הרשאה לבדוק |
| `OGENPLAY_SCHEDULE_VUS` | `5` | מספר משתמשים מקבילים; 1–100 |
| `OGENPLAY_SCHEDULE_DURATION` | `1m` | משך הבדיקה; `1m`, `3m` או `5m` |
| `OGENPLAY_SCHEDULE_MIN_WAIT_SECONDS` | `1` | זמן המתנה מינימלי בין בקשות של כל משתמש |
| `OGENPLAY_SCHEDULE_MAX_WAIT_SECONDS` | `3` | זמן המתנה מקסימלי בין בקשות של כל משתמש |

אחרי הוספת המשתנים, GitHub יתחיל להריץ בדיקה אוטומטית לפי לוח הזמנים. אם אחד משני משתני ההפעלה/האישור חסר או אינו `true`, הריצה המתוזמנת תסתיים בלי לשלוח בקשות לאתר. כדי להפסיק את הבדיקות, הגדירו `OGENPLAY_SCHEDULE_ENABLED=false` או מחקו את המשתנה.

### שינוי כמות המשתמשים וקצב הבקשות

- לשינוי עומס מקבילי עדכנו את `OGENPLAY_SCHEDULE_VUS`. התחילו ב־5 והעלו בהדרגה; במסלול האוטומטי התקרה היא 100 משתמשים.
- לשינוי תדירות הבקשות של כל משתמש עדכנו את `OGENPLAY_SCHEDULE_MIN_WAIT_SECONDS` ואת `OGENPLAY_SCHEDULE_MAX_WAIT_SECONDS`. הערכים מותרים בין 1 ל־30 שניות, והמקסימום חייב להיות לפחות המינימום. לדוגמה, `2` ו־`4` פירושם המתנה אקראית של 2–4 שניות אחרי כל תגובה.
- חשוב: מרווח ההמתנה הוא אחרי כל תגובת HTTP. קצב הבקשות בפועל תלוי גם בזמן התגובה של האתר; זו אינה הבטחה למספר קבוע של בקשות בשנייה.

### שינוי תדירות ההרצה האוטומטית

פתחו את [קובץ התזמון](.github/workflows/scheduled-load-test.yml) וערכו את שורת ה־cron:

| תדירות | ערך cron |
| --- | --- |
| כל שעתיים | `17 */2 * * *` |
| כל 3 שעות | `17 */3 * * *` |
| כל 4 שעות — ברירת מחדל | `17 */4 * * *` |
| כל 6 שעות | `17 */6 * * *` |
| פעם ביום בשעה 03:17 | `17 3 * * *` |

השאירו את `timezone: 'Asia/Jerusalem'` כדי להשתמש בשעון ישראל, כולל שינויי שעון קיץ וחורף. שמרו את השינוי ומזגו אותו ל־`main`; GitHub מפעיל לוחות זמנים רק מתוך ענף ברירת המחדל. ריצות מתוזמנות עלולות להתעכב בעומס של GitHub Actions, והן אינן מערכת ניטור עם התחייבות לשעת התחלה מדויקת.

### הפעלה ידנית מיידית

אפשר להריץ את אותו workflow בלי לחכות למועד הבא: פתחו [Actions](https://github.com/mh0774020798-droid/ACRASA-CSS2/actions), בחרו **⏰ בדיקת עומס אוטומטית — עוגן פליי**, לחצו **Run workflow**, קבעו משתמשים, משך, מרווחי המתנה וסמנו `authorize_target`. ההרצה הידנית מתחילה אחרי ש־GitHub מקצה runner.

**הבדיקות האוטומטיות מוגבלות ל־100 משתמשים** כדי לצמצם את הסיכון להפלת האתר בבדיקת לילה/סוף שבוע. בדיקות של אלפים ומעלה נשארות במסלול המבוזר להפעלה ידנית, בחלון תחזוקה מתואם, ולא כחזרה בלתי מפוקחת כל כמה שעות. גם 100 משתמשים יכולים לייצר עומס ניכר; התחילו ב־5 ובדקו משאבי שרת, CDN ולוגים לפני הגדלה.

## 🌐 בדיקה גדולה: עד 100,000 משתמשים במקביל

לכמות גדולה פתחו ב־**Actions** את **🌐 בדיקת עומס גדולה — עד 100,000 משתמשים**. זהו מסלול נוסף עם כמה מחשבי בדיקה מסונכרנים.

לחצו **Run workflow**, בחרו `main` והזינו:

| שדה | עבור היעד של 100,000 |
| --- | --- |
| `total_vus` | `100000` (יש להקליד ידנית; ברירת המחדל היא 100) |
| `shard_count` | `19` (יש להקליד ידנית; ברירת המחדל היא 1) |
| `duration` | `3m` |
| `runner_type` | `github-hosted` |
| `authorize_target` | `true` (אישור מפורש לבדיקת עומס באתר שבבעלותכם או שיש לכם הרשאה לבדוק) |

החלוקה מדויקת: 3 מחשבים מקבלים 5,264 משתמשים כל אחד, ו־16 מחשבים מקבלים 5,263. יחד: 100,000. אלה משתמשים מדומים פעילים שמבקשים עמוד וממתינים בין בקשות; אין הכוונה ל־100,000 בקשות באותה אלפית שנייה.

**100,000 משתמשים מדומים הם בדיקת קצה שעלולה להאט או להפיל את האתר.** התחילו ב־5, אחר כך 25, 100 ו־1,000, ובדקו את משאבי השרת ואת לוגי האתר בין שלב לשלב. העלאה ל־100,000 נעשית ידנית בלבד, ורק לאחר תיאום חלון בדיקה ואישור מפורש של בעל האתר.

כך מתבצעת הריצה הגדולה:

1. 🧮 נבנית תוכנית עם חלוקת המשתמשים המדויקת.
2. ⏸️ כל מחשב מפעיל k6 במצב עצור ומכין את כל המשתמשים שלו. נבדקים מספר המשתמשים שהוכנו והזיכרון.
3. 🧭 המתאם ממתין שכל המחשבים יהיו מוכנים. אם חסר מחשב אחרי 10 דקות, העומס אינו משוחרר.
4. 🟢 מפורסם מועד משותף בעוד 45 שניות, וכל המחשבים מתחילים את התרחיש ההדרגתי יחד.
5. 📊 נאספים מונים, שגיאות ודגימות שיא מכל המחשבים. כדי לאמת את הכמות הכוללת נדרשים חלונות שיא חופפים בכל המחשבים.

ברירת המחדל של המסלול הגדול היא 100 משתמשים ומחשב אחד. כדי לבחור 100,000 יש להזין ידנית `100000` ו־`19`. בחשבון GitHub Free מכסת המקביליות הרגילה היא 20 עבודות. המסלול משתמש ב־19 מחשבי עומס ומחשב מתאם אחד. עבודות אחרות באותו חשבון או מחסור זמני במחשבים יכולים לגרום להמתנה. הכנת 100,000 המשתמשים תלויה בזיכרון, CPU ורשת; המספר המוזן הוא יעד, ואינו הוכחה שהעומס נוצר.

ניטור מקומי מפסיק מחשב בדיקה אם הזיכרון שלו מתקרב למגבלה, או אם עומס CPU גבוה נמשך בכמה דגימות. כישלון של מחשב אחד מבטל את יתר עבודות העומס באותו מערך. הדוח מבחין בין בעיה במחשב הבודק לבעיה בתשובות האתר. הניטור אינו מכסה כל מגבלת רשת אפשרית.

בסיום פתחו את הריצה ואת הדוח של **📊 דוח משולב: יעד, שיא שאומת ותקלות**. באזור **Artifacts** הורידו את `ogenplay-combined-report-...`, חלצו ופתחו `report.html`. מוצגים היעד המבוקש, הכמות שאומתה בדגימות חופפות, מונים משולבים ותוצאות לכל מחשב. בדוח חלקי הכמות הכוללת מוצגת כלא מאומתת.

הממוצע משוקלל לפי מספר הכניסות מכל מחשב. **p95 מוצג כ־p95 המקומי הגבוה ביותר בין המחשבים; הוא אינו p95 גלובלי.** לא מחברים או ממוצעים אחוזונים כדי להמציא אחוזון כולל.

אם מחשבי GitHub אינם מספיקים, אפשר לבחור `self-hosted`. נדרשים אז מחשבי Linux x64 ייעודיים שכבר חוברו למאגר עם התווית `ogenplay-load`, Python 3 ו־sudo. הגדירו runner אחד לכל מחשב, שעונים מסונכרנים וקישוריות ל־GitHub ולאתר. המסלול אינו רוכש או מקים שרתים.

הריצה הגדולה והריצה הרגילה משתמשות באותה קבוצת מקביליות, ולכן לא יוצרות עומס על האתר יחד. להפעלה חוזרת של ריצה גדולה בחרו **Re-run all jobs**, או פתחו **Run workflow** חדש; יש להכין ולסנכרן מחדש את כל המחשבים. ביטול הריצה כולה עשוי למנוע השלמת איסוף הדוחות.

בדיקות הקוד מאמתות את החשבון של 100,000 ואת מנגנון prepare/pause/resume מול שני תהליכי k6 ושרת דמה מקומי. הן אינן מבצעות הרצה של 100,000 מול האתר.

## ▶️ הפעלה ב-GitHub

1. מזגו את בקשת השינוי ל־`main` לאחר שהבדיקות האוטומטיות עברו.
2. פתחו את לשונית **Actions** במאגר. אם GitHub מבקש להפעיל Actions במאגר שהועתק, אשרו את הפעלתם.
3. בחרו **🚀 בדיקת מהירות האתר עוגן פליי**.
4. לחצו **Run workflow** ובחרו בענף **main**.
5. השאירו `total_vus` על **5** ואת `duration` על **1m** להרצה ראשונה, סמנו `authorize_target` לאישור הרשאה מפורשת, ולחצו **Run workflow**.
6. פתחו את הריצה ואת השלב **🚀 בדיקת זמינות, עלייה בעומס ומדידת מהירות** לצפייה בלוגים.
7. בסיום חזרו ל־**Summary** של הריצה. דוח בעברית יופיע שם גם כאשר המדידה נכשלת. באזור **Artifacts** אפשר להוריד את `ogenplay-performance-report-...`, לחלץ ולפתוח את **report.html** בדפדפן.

זמן הריצה כולל גם הכנת סביבת GitHub, התקנת הכלי וסיום בקשות פעילות; לכן בחירה של דקה אינה מבטיחה שהריצה כולה תסתיים בתוך דקה.

אפשר לעצור ריצה דרך **Cancel workflow**. אם בוטלה הריצה כולה, GitHub עשוי שלא להשלים את יצירת הדוח או העלאתו. במקרה כזה נשארים הלוגים שכבר הודפסו.

## ⚙️ מה בוחרים?

| שדה | משמעות | התחלה מומלצת |
| --- | --- | --- |
| `total_vus` | מספר המשתמשים המדומים בשיא. כל מספר שלם בין 1 ל־100 | 5 |
| `duration` | משך תרחיש המדידה: דקה, 3 דקות או 5 דקות | 1m |

הכתובת מוגדרת בקוד ל־**https://ogenplay.com/**. הבדיקה נעצרת מראש אם הדומיין שונה או אם לא מסמנים את אישור ההרשאה ב־GitHub Actions. מספר המשתמשים הוא מספר פעולות הבדיקה במקביל, ולא מספר הבקשות בשנייה.

אם בדיקה ראשונה עוברת, אפשר לבדוק בהמשך 10 או 25 משתמשים ולהשוות. בדיקת עומס יכולה להאט את האתר בזמן הריצה; התחילו בכמות קטנה. המגבלה של 100 היא גבול הכלי הזה, ואינה קביעה שהאתר יעמוד בעומס כזה.

המסלול הרגיל מפעיל תהליך מדידה אחד. הרצות של בדיקת העומס באותו מאגר אינן פועלות זו לצד זו. בדיקות קוד אוטומטיות פונות רק לשרת דמה מקומי, ולא לאתר החי.

## 🧠 איך הבדיקה עובדת, שלב אחרי שלב?

1. **🧭 בדיקת זמינות:** נשלחת בקשה אחת לעמוד הבית. חייבים לקבל HTTP 200 ולזהות בתשובה את הטקסט `עוגן פליי`. אחרת הבדיקה נעצרת עם הסבר. בקשה זו אינה נכללת במוני הכניסות של דוח העומס.
2. **🟦 עלייה בעומס:** מתחילים ממשתמש מדומה אחד ועולים לכמות שבחרתם במשך כ־20% מהזמן.
3. **🟩 עומס השיא:** הכמות שבחרתם נשמרת במשך כ־60% מהזמן.
4. **🟨 ירידה בעומס:** מספר המשתמשים יורד לאפס במשך כ־20% מהזמן.
5. **📊 סיכום:** מופיעים זמני תגובה, מוני כניסות, שיעור תקלות, סוגי התקלות והסבר האם היעדים הושגו.

לדוגמה, ב־5 משתמשים למשך דקה: עולים ל־5 במשך 12 שניות, נשארים ב־5 במשך 36 שניות ויורדים לאפס במשך 12 שניות. בקשות שכבר התחילו מקבלות זמן נוסף לסיום.

כל משתמש מדומה מבצע את הפעולה הבאה שוב ושוב: מבקש את עמוד הבית, בודק את התגובה, ממתין בין שנייה ל־3 שניות וחוזר. אין יצירת חשבונות או התחברות לאתר.

התקדמות ודוגמת כניסה מודפסות בערך אחת ל־15 שניות ממשתמש מדומה אחד, בהתאם לזמן תגובות האתר. אלה דוגמאות; הדוח הסופי כולל את **כל** הכניסות. כדי לשמור על לוג קריא מודפסות עד 3 דוגמאות תקלה מאותו משתמש.

## 🎯 מה נחשב מעבר של הבדיקה?

- **מהירות:** p95 נמוך מ־3,000 מילישניות.
- **תקינות:** פחות מ־2% מהכניסות נכשלו.
- **עצירה בעת תקלות רבות:** אחרי השהיה של 30 שניות, אם שיעור הכישלונות הכולל מגיע ל־10% או יותר, k6 עוצר את הבדיקה בהערכת הספים הבאה. השהיה זו אינה הבטחה לעצירה בדיוק בשנייה ה־30.

היעדים הם כללי ההערכה שנבחרו לבדיקה זו. קוד סיום 0 פירושו שהמדידה עברה; 99 פירושו חריגה מיעד, ויכול להופיע גם בעת עצירה בגלל יעד השגיאות. בקשת שינוי או ריצה עם סימון אדום אינה אומרת בהכרח שהקוד התקלקל: ייתכן שהאתר פשוט לא עמד ביעדים.

אין להסיק מהרצה שעברה עם 5 משתמשים שהאתר יתמוך באלפים. אם הבדיקה לא התחילה, נעצרה מוקדם, או שאין מספיק נתונים, הדוח אינו מציג אותה כהצלחה.

## 🔎 פירוש שגיאות

| הודעה | משמעות ומה לבדוק |
| --- | --- |
| 🚫 403 | הגישה נחסמה. ייתכן כלל אבטחה או הרשאות; בדקו את הגדרות האתר והלוגים |
| 🚦 429 | האתר מגביל את קצב הבקשות. הקטינו את מספר המשתמשים ובדקו את ההגבלה |
| 🖥️ 5xx | שגיאה מהשרת או משירות מתווך. בדקו לוגים ושימוש במשאבים בזמן הבדיקה |
| 🔌 אין תגובת HTTP | ייתכן timeout, DNS, TLS או תקלה ברשת. המדד לבדו אינו קובע את הסיבה |
| 📄 תגובה לא צפויה | למשל 404, הפניה או עמוד עם HTTP 200 שאינו מכיל את שם המותג עוגן פליי |

בקשה בודדת ממתינה עד 10 שניות. הפניות אינן נעקבות: אם האתר מתחיל להפנות לכתובת אחרת, יש לבדוק את ההפניה לפני התאמת הבדיקה.

## 📏 מה המדידה יכולה לומר?

זו בדיקת HTTP של עמוד הבית מנקודת המדידה ב־GitHub. היא אינה דפדפן מלא: אין הורדת תמונות ו־CSS, הרצת JavaScript, ציור מסך, שימוש ב־WebSocket, התחברות או כתיבת פוסטים. לכן היא אינה מודדת את כל חוויית הגלישה.

אם שירות מטמון או CDN עונה לבקשות, המדידה כוללת גם אותו. המיקום והרשת של מחשב המדידה יכולים לשנות את התוצאה; התוצאה אינה זמן הטעינה של כל גולש בישראל.

## 💻 הרצה מקומית למי שמעוניין

נדרשים k6 **1.4.0** ו־Python 3. ה־workflow משתמש בגרסה קבועה של k6 כדי לשמור על מבנה מדדים עקבי.

```bash
TOTAL_VUS=5 TEST_DURATION=1m k6 run load-test.js
python3 summarize.py summary.json --markdown report.md --html report.html
```

ב־PowerShell:

```powershell
$env:TOTAL_VUS = "5"
$env:TEST_DURATION = "1m"
k6 run load-test.js
python summarize.py summary.json --markdown report.md --html report.html
```

`summarize.py` קורא גם את המבנה המקונן של `handleSummary` וגם את המבנה השטוח של `summary-export` הישן. בדוחות ישנים מדדי הכניסות וסיבות השגיאה החדשים אינם זמינים.
